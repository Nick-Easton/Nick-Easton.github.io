给博客加一个
国内访问镜像

从访问链路到部署参数，完整记录第二个发布入口是怎样建立的。

2026 年 7 月 13 日 阅读约 12 分钟 Nick

博客发布到 GitHub Pages 以后，代码管理和版本记录都很方便，但国内访客会受到 GitHub 网络状况影响。为了不放弃现有工作流，同时降低访问门槛，我为同一份博客代码增加了腾讯云 CloudBase 镜像。本文把这次操作整理成一份可以复习的部署笔记。

先弄清问题发生在哪里

在开始部署之前，需要把 Git、GitHub 和 GitHub Pages 区分开。Git 是电脑上的版本管理工具；GitHub 是存放 Git 仓库的远程平台；GitHub Pages 则负责把仓库里的静态文件变成网站。国内访客打不开博客，通常不是博客代码损坏，而是访问 GitHub Pages 服务器的网络链路不稳定。

只给 GitHub Pages 换一个更短的自定义域名，并不会改变网页文件实际所在的服务器。浏览器最终仍要连接 GitHub 的基础设施，所以域名更好记，却不一定能解决访问问题。

这次的目标不是搬走 GitHub，而是让同一份代码拥有第二个、位于不同基础设施上的发布入口。

这里所说的“镜像”也不是两台服务器实时复制数据。更准确地说，是让两个托管平台分别部署 GitHub 仓库中的同一个版本：GitHub Pages 保留为原地址，CloudBase 成为面向国内访客的测试地址。

完成本文的过程后，需要能够回答三个问题：源代码保存在哪里、访客实际连接哪台服务器、代码更新后由谁负责重新发布。

理解完整的访问与部署链路

整个系统只保留一份“可信源代码”，也就是 GitHub 仓库。开发电脑负责修改代码，GitHub 负责保存版本，托管平台负责把某个提交转换成访客可以访问的网站。

开发电脑
  │  git push
  ▼
GitHub 仓库（唯一代码源）
  ├── GitHub Pages ──────────────► 原访问地址
  └── CloudBase 拉取指定分支
          │
          ▼
      静态托管存储（源站）
          │
          ▼
      CDN 边缘节点 ──────────────► 国内测试地址

静态托管指的是直接保存和分发 HTML、CSS、JavaScript、图片等文件，不运行长期在线的应用服务器。本博客没有登录、数据库或服务端渲染，因此部署时不需要配置端口、进程和服务器运行环境。

源站是托管平台保存原始文件的位置；CDN会把常用文件缓存到距离访客更近的边缘节点；HTTPS负责加密浏览器与站点之间的连接。CloudBase 把这三部分组合起来，所以部署完成后不需要自己购买服务器或配置 Nginx。

这种架构最大的好处是不会出现“GitHub 一份、腾讯云一份，改完还要手动复制”的混乱。只要两个发布入口都指向同一个仓库和正确分支，版本关系就能保持清楚。

部署前需要准备什么

本次部署使用了以下资源：

  • GitHub 仓库：Nick-Easton/Nick-Easton.github.io。
  • 部署分支：agent/blog-foundation。
  • CloudBase 环境名称：nick-blog-test。
  • CloudBase 环境 ID：nick-blog-test-d6gor1sd1da2c5d15。
  • 地域：上海；套餐：六个月免费体验版。

仓库必须包含可以直接访问的 index.html。文章页面放在 posts/ 目录，样式和脚本位于仓库根目录。部署前还需要确认本地修改已经提交并推送，否则 CloudBase 只能拉取 GitHub 上的旧版本。

git status
git branch --show-current
git log -1 --oneline
git push

首次验证使用“公开仓库部署”：CloudBase 可以直接读取公开代码，因此不需要把腾讯云密钥写进项目，也不需要立刻授予 GitHub 账户权限。这种方式适合先确认目录和页面能否正确发布，但本次实测发现它只保存了仓库地址，并不会在每次 git push 后自动创建新版本。

理论上，要让推送自动触发部署，需要把服务更新为“Git 个人仓库部署”，并通过 GitHub 官方授权页允许 CloudBase 读取仓库和管理部署所需的触发器。但“已授权”只说明账户连接成功，不能代替实际触发测试。对于私有仓库同样应使用平台提供的授权流程或专门的密钥管理功能，绝不能把 SecretKey、访问令牌或 API Key 直接提交到 Git。

控制台部署步骤与参数解释

第一步是在腾讯云 CloudBase 创建环境。免费体验版需要领取兑换码，确认订单金额为 0 元后完成开通。新环境创建后可能会短暂显示“状态异常”或“正在初始化”，这时应等待资源准备完成并刷新页面，而不是重复购买环境。

第二步进入“静态网站托管”，先选择“公开仓库部署”，填写仓库地址并选择目标分支。这个步骤决定 CloudBase 从哪里取得代码：

仓库地址：https://github.com/Nick-Easton/Nick-Easton.github.io.git
仓库分支：agent/blog-foundation
项目名称：nick-blog-mirror

第三步是最容易出错的构建配置。本项目不使用 npm，也没有 dist 目录，所以采用下面的参数：

项目框架：其他
目标目录：./
安装命令：（留空）
构建命令：（留空）
构建产物目录：./
部署路径：/
  • 目标目录表示仓库中项目源代码的位置。博客就在仓库根目录，因此是 ./。
  • 安装命令用于下载项目依赖。本项目没有 package.json 和依赖，必须留空。
  • 构建命令用于把源代码编译成发布文件。纯 HTML 项目不需要编译，同样留空。
  • 构建产物目录是最终要上传的文件夹。这里直接上传仓库根目录，所以填写 ./，不能沿用默认的 ./dist。
  • 部署路径决定网站挂载位置。填写 / 后，index.html 会成为域名根路径的首页。

确认后，CloudBase 会依次检出代码、准备构建环境、执行部署命令并上传文件。第一次部署日志显示共上传 17 个文件、失败 0 个，最终生成 tcloudbaseapp.com 测试域名。加入本文后再次部署，日志显示共上传 18 个文件，其中包括 /posts/cloudbase-mirror-deployment.html，失败仍为 0 个。

怎样判断部署真的成功

看到控制台显示“成功”只是第一层检查。一个网站是否可用，还需要分别验证网络响应、资源加载和页面功能。

  • 网络响应：首页和所有重要页面都应返回 HTTP 200，而不是 404 或 5xx。
  • 静态资源：CSS、JavaScript 和图片应正常加载，页面不能只有无样式的文字。
  • 直接访问：把文章地址粘贴到新标签页，确认不经过首页也能打开。
  • 站内导航：依次测试分类、归档、搜索、关于我和文章链接。
  • 响应式布局：在窄屏下检查导航、正文和文章目录是否溢出。

本次检查的首页、分类、归档、搜索、关于我和第一篇文章全部返回 200。使用 PowerShell 可以快速检查某个地址的状态码：

$url = "https://测试域名/categories.html"
$response = Invoke-WebRequest -Uri $url -Method Head
$response.StatusCode

状态码正常不代表交互一定正常，所以仍要在浏览器中打开页面。更新 JavaScript 数据文件后，还要注意浏览器或 CDN 缓存；给文件地址增加版本参数，例如 articles.js?v=2，可以让浏览器请求新版本。

Git 推送如何触发后续更新

只填写公开仓库地址并不等于已经建立自动更新。理想情况下，GitHub 收到目标分支的推送后会通知 CloudBase，CloudBase 再拉取对应提交并创建新版本。为建立这条链路，我在服务的“更新服务”页面把部署方式确认成“Git 个人仓库部署”，点击 GitHub 授权，并重新核对了以下信息：

授权账户：Nick-Easton（个人账户）
Git 仓库：Nick-Easton/Nick-Easton.github.io
监听分支：agent/blog-foundation
构建产物目录：./
部署路径：/

授权属于账户权限变更，应该由仓库所有者本人完成。授权页会列出 CloudBase 申请的仓库读取和触发器管理权限；确认登录账户、应用名称和权限范围后再同意。如果以后不再使用自动部署，可以在 GitHub 的应用授权设置中撤销访问权限。

本次测试使用提交 46ac2fa 验证自动触发：推送后持续刷新部署版本列表，但列表仍只有手动创建的 nick-blog-mirror-001 和 nick-blog-mirror-002，没有出现第 3 个版本；仓库的普通 Webhook 列表也为空。因此，目前只能确认 GitHub 授权和手动拉取成功，不能确认自动部署已经建立。

判断自动部署是否成功，必须看到“推送之后、没有点击部署按钮，却自动产生了新版本”。只看到“已授权”或手动部署成功，都不算验证通过。

当前服务最初由“公开仓库部署”创建，后来再更新为个人仓库部署。触发失败可能与旧服务的创建方式或平台级授权机制有关；在没有更多日志证据前，这只是一项排查方向，而不是已经证实的原因。下一步应在保留现有可访问站点的前提下，重新创建个人仓库部署服务进行对照测试。

当自动触发真正建立以后，任意电脑上的开发流程才会变成先同步远程修改，再编辑、检查、提交并推送：

git pull --ff-only
# 编辑并在本地预览
git status
git add .
git commit -m "新增或更新博客文章"
git push

git push只负责把新提交送到 GitHub。若触发链路工作正常，CloudBase 会随后拉取指定提交并创建新的部署版本；若版本列表没有变化，就要把它当作“未触发”继续排查，而不能假设网站已经更新。访客不需要访问 GitHub，也不需要登录腾讯云，他们只访问已经发布的镜像域名。

分支必须保持一致。目前 CloudBase 监听 agent/blog-foundation，如果以后把博客正式合并到 main，就要同步修改 CloudBase 的部署分支，否则推送到 main 不会更新镜像。

发布不是瞬间完成的。推送后应到“应用部署列表”确认新版本状态为成功，再打开网站检查。CDN 节点和浏览器缓存也可能让旧内容短暂存在，因此不要在几秒内反复修改部署配置。

常见问题与正式上线计划

这类静态部署出现问题时，可以按“仓库版本 → 构建日志 → 上传目录 → 浏览器请求”的顺序排查：

  • 首页 404：检查构建产物目录里是否真的存在 index.html，以及部署路径是否为 /。
  • 只有首页能开：确认其他 HTML 文件和 posts/ 文件夹已经上传，链接大小写与真实文件名一致。
  • 样式或图片丢失：在浏览器开发者工具中查看资源是否 404，并检查相对路径层级。
  • 更新后内容没变化：先确认提交已经推送到正确分支，再检查 CloudBase 是否生成了新部署版本，最后排除缓存。
  • 中文显示乱码：确保文件使用 UTF-8 保存，并在 HTML 的 <head> 中声明 <meta charset="UTF-8">。
  • 构建失败：从日志中找到第一个错误，而不是只看最后一行；重点检查仓库拉取、目录和命令配置。

当前域名是 CloudBase 默认测试域名，地址较长，并且官方明确将它定位为开发测试用途。正式面向访客时，还需要购买容易记住的自定义域名、根据中国大陆节点的要求完成 ICP 备案，并配置域名解析、HTTPS、缓存和基础安全限制。

这次部署让我第一次完整理解了从代码仓库到访客浏览器之间的链路：Git 管版本，GitHub 保存代码，CloudBase 执行发布，静态托管保存文件，CDN 负责分发。博客不再只是电脑里的项目，而是拥有了可以持续维护的第二个公开入口。
